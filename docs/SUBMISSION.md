# Submission Form

#### 1. Project description: describe your project and what problem it solves

GearFlow is an agentic interface for computational fluid dynamics. Describe the simulation you want, and an agent sets it up, runs it, and explains the results. Traditional CFD tools are powerful, but setting up a simulation takes hours of meshing, solver configuration, and plotting before any insight appears. Students can ask questions and receive instant visual feedback with physics explanations. Engineers can test simple ideas without wasting compute resources on expensive simulations.

GearFlow simplifies setup to a sentence. Type "Set up an airfoil naca 2415 at angle of attack 6" and an agent builds the case live: airfoils, cylinder wakes, square blocks, orifice constrictions, with pressure, velocity, and lift reading out beside the field. The "Physics Agent" explains what changed, why, and what to try next in plain language. The demo is the agentic loop itself: describe the physics you want, the agent sets it up, runs it, and explains it. The current solver is a 2D inviscid estimation; Planned next steps is a built-in viscous solver that the agent drives end to end for real CFD simulations.

#### 2. Describe your use of Meta products to build the submitted project

One live Meta integration, used deeply rather than broadly: Muse Spark (served as gearflow-chat through Modal behind a same-origin proxy) powers the entire chat harness. Every turn runs the same pipeline: user words go through the proxy to the model with reasoning locked down (single completion, capped length at 400 tokens, temperature forced to 0, low reasoning effort); the model answers only in a fenced envelope of actions; a validator checks each action against a strict contract (five-action cap, envelope floors on alpha and Reynolds number); the app executor applies them to the solver; the physics agent then explains what changed, why, and what to try next. Every call is hash-cached (24-hour TTL), logged to an eval ledger with latency, token, and cost figures, and governed by a $5 session spend cap with fail-closed honest errors plus Retry. SAM 3.1 segmentation and Muse Image poster paths exist in the codebase but are deliberately unmounted in this build, a documented single-model scope decision trading breadth for reliability.

#### 3. Why are Meta's models important to your solution?

The agent is the product, and the agent is reasoning. Deterministic parsers cover only exact keywords ("alpha," "thicker"); everything that makes the demo feel intelligent happens in the model: interpreting "increase camber and decrease thickness" as a complete airfoil re-specification, bridging "constricted" to the orifice path, deciding when a question deserves a pressure-field switch versus a text answer, and teaching stall intuition in plain grade-school language grounded in live lift and pressure numbers. The forced determinism settings are equally load-bearing: temperature zero and single-completion output turn a chatbot into an instrument whose actions validate against a contract on every turn. Without the Meta reasoning model there is no natural-language setup, no tutor, and no core loop.
